# REVIEW_PROCESS：分层审批与预期预判协议

> 适用范围：小白龙 × 用户 的日常代码/策略工作协作。
> 核心原则：审批成本花在"不可逆"上，不花在"每一步"上。每波工作以"预期预判"打底，契约性审批，达标自动续跑，不达标自动停。

---

## 一、预期预判（每波启动前，先打底，再动手）

任何一波工作开始前，先产出**四层预判**，随工作简报一起给出。用户批的是这四层，不是每一步动作。

| 层 | 预判内容 | 回答的问题 |
|---|---|---|
| L1 目标层 | 这波要解决的用户问题（一句话 WANT） | 用户真正要什么？ |
| L2 交付层 | 用户期待看到的具体产出（文件/功能/数字/状态） | 什么算"做完了"？ |
| L3 验收层 | 可执行验收标准：测试命令、通过条件、改动文件清单、停下条件 | 怎么证明做完了？ |
| L4 风险层 | 红线清单（用户一定在意的操作）+ 自动停下条件 | 哪里最可能出事、何时该停？ |

预判产出 → 用户确认或纠正（批契约）→ 推进。

## 二、风险分档（人工只守高险档）

| 档位 | 内容 | 审批方式 |
|---|---|---|
| A 档（免审直推） | 测试修复、注释、纯重构、格式化、低风险脚本 | 直接做，攒波推送，事后汇报 |
| B 档（波次审批） | 新功能、新表、API 变更、策略逻辑改动 | 每 3~5 commit 汇报一次，附 diff stat + 测试结果，达标续跑 |
| C 档（逐项停） | 破坏性 schema、数据迁移/删除、推送 GitHub、安全策略变更 | 逐项人工确认，未确认不动 |

## 三、执行节奏

1. **启动**：写四层预判 → 用户批契约。
2. **推进**：A 档直接做；B 档到波次节点汇报（diff stat + 测试）；C 档停下等确认。
3. **收口**：达标汇报（测试全绿 + 改动清单 + 状态）；不达标原地停下，说明具体阻塞，不绕过。

## 四、回滚兜底（安全感的真正来源）

- 每波独立 commit，粒度可回溯。
- 库变更先走 snapshot 快照（snapshot.rs），出问题精确回退。
- 可回滚是比审批更硬的安全网——这正是"不必每一步都批"的底气。

## 五、红线清单（C 档固定项，只增不减）

- [ ] git push 到远端
- [ ] 破坏性 schema / 数据删除 / 数据迁移
- [ ] 安全策略（token、限流、端口、权限）变更
- [ ] 用户明说"先别动/等我确认"的路径

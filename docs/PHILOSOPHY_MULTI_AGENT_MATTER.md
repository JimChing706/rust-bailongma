# 多Agent事项哲学底层：探索框架 v1

> 状态：探索性文档（非规范）
> 关联代码：`agents/`（探测/委托）、`evolution/`（收敛/快照/蒸馏）、`approval.rs`（审批门）、`llm/`（工具循环/台账）、`trace.rs`、`memory/`
> 原则：工程问题最终是概念问题。先问"事项是什么"，再问"事项怎么管"。

---

## 〇、为什么需要哲学底层

多Agent系统的大部分故障，不是代码 bug，是概念含混：

- Agent 自作主张干了没被要求的事 → 我们没定义"事项从哪来"（意图的转译边界）
- 子任务拆了等于没拆，执行完发现合不上 → 我们没定义"什么才算一个可独立验证的子事项"
- 任务失败后互相推诿、无法归因 → 我们没定义"事项的作者/执行者/验证者分别是谁"
- 半途而废的旧事项反复冒出来干扰 → 我们没定义"事项如何死亡"

代码层已经有大量隐式的哲学回答（审批门、收敛判据、delegated_from、幂等键）。这份文档把这些回答显式化、体系化，并指出缺口。

---

## 一、事项本体论：一个"事项"是什么？

**命题 1：事项不是物，是差距。**

一个事项的本质，是"期望状态"与"当前状态"之间的差（gap），由某个意图主体（人）给出，并以承诺形式存在：

> "某状态 S 将在未来被达成" —— 这是一份欠世界的债。

- 事项在被达成之前是"半存在"的：它有方向（朝向 S），没有实体。
- 事项的强度 = 差距的大小 × 承诺的严肃度（谁承诺的、有没有验收标准）。
- 没有验收标准的"事项"不是事项，是愿望。愿望不欠债。

**工程映射：**
- 现有 `evolution/convergence.rs` 的"收益分单度量"已经是差距度量的雏形——它在问"这次改动离目标状态近了多少"。
- 缺口：**没有"事项创建时的验收标准"字段**。现在事项隐含在 prompt 里，验收标准隐含在用户脑子里。→ 设计约束：任何持久化事项必须携带 `verifiable: bool`（是否可验证）与验收判据，不可验证的事项只允许作为草稿存在。

## 二、意图的转译：从"想要"到"要做"

**命题 2：意图转译是系统的原罪之地。**

用户一个模糊愿望（"把项目优化一下"）变成可执行事项，中间隔着翻译：模糊 → 明确 → 可验证。每一步都是信息损失。

- 转译链断裂的第一种形态：**事项漂移**——Agent 把"优化一下"自己翻译成"重构整个架构"，用户没批准，Agent 已开工。漂移的本质是 Agent 篡改了差距的定义。
- 转译链断裂的第二种形态：**事项缩水**——Agent 把复杂事项悄悄替换成它顺手能做的子集，报告"完成"。

**工程映射：**
- 现有防线：`approval.rs` 审批门 = 关键转译点需要人确认；`grant_agent_delegation` = 委托权限是显式授予的。
- 缺口：**转译的语义漂移没有度量**。Agent 执行前后，用户意图的"距离"无法量化。→ 设计约束：多轮事项应保留"意图原句"，在收敛报告中给出"我把它理解为 X，做成了 Y"的对照，让漂移可见。

## 三、分解的哲学：一个事项何时是"一个"？

**命题 3：可分性不是天然的，是实用主义的。**

事项能否拆分，不取决于它"看起来"多大，而取决于**是否存在可独立验证的中间态**。

- 真分解：每个子事项有独立验收点，合起来能还原母事项的验收标准（可加性）。
- 假分解：子事项只是步骤清单，互相纠缠，无法单独验证——拆了等于没拆，还多了协调成本。

多Agent里"为架构而架构"的病根就在这：先决定要多个 agent，再倒过来把事项硬切成几块，切出来的都是假分解。

**工程映射：**
- 现有 `agents/delegate.rs` 的 `delegate_to_agent` 是把一个事项整体委托（prompt 是"唯一指令"），粒度由调用方决定。
- 缺口：**没有"分解合法性"检查**。→ 设计约束：委托/分解工具应接受"母事项验收判据 + 子事项验收判据"，由调用方声明可加性；声明为可加而执行后合不上的，记入台账作为分解质量信号。

## 四、责任与归属：事项的"作者"是谁？

**命题 4：一个事项同时有三个主体——发起者、执行者、验证者，它们不必是同一个人。**

- 发起者（origin）：意图的源头。只有它有权修改验收标准。
- 执行者（executor）：干活的人。多Agent协作中可以有多个，但同一时刻的同一子事项只有一个执行者（否则责任稀释）。
- 验证者（verifier）：对照验收标准判定完成/未完成。**验证者不能是执行者自己**——否则就是自己给自己判卷。

责任归属失败的多Agent系统，表现为"群体性免责"：每个 agent 都做了一点，失败时谁都说不清是哪一步的错。

**工程映射：**
- 现有：`llm_tool_calls` 台账带 `delegated_from`（谁派发的）、`trace.rs`（工具调用轨迹）、幂等键带 attempt 维度——**归因骨架已经在**。
- 缺口：**验证者角色未实体化**。现在"完成"由执行者自报，验收由用户事后看。→ 设计约束：高风险事项应显式指定 verifier（可以是另一个 agent、规则检查器、或人）；verifier == executor 时降低该事项的可信等级。

## 五、语言与行动：prompt 与世界的缝隙

**命题 5：多Agent是语言社会，但事项必须在世界中被达成。**

LLM 是语言模型：它的一切操作是符号操作。事项的达成却需要世界状态改变（文件变了、进程跑了、钱转了）。语言描述与真实达成之间永远有缝隙——**符号落地问题**。

- 缝隙的正面：工具调用（exec/sandbox/write_file）是"语言跨到世界"的桥。桥越窄（参数 schema 越严、沙箱越硬），缝隙越小。
- 缝隙的反面：Agent 之间互相传递的 prompt，是"关于事项的语言"，不是事项本身。A 告诉 B"文件已改好"，B 只能信；除非 B 去读文件。

多Agent 的信任问题本质是：**语言承诺 vs 世界事实**。信任来自可复核（verifiable），不来自诚意。

**工程映射：**
- 现有：`tools/` 的 NativeToolExecutor、sandbox 子进程 JSON-RPC、`llm/replay.rs` 防重放——都是在收窄缝隙。
- 缺口：**跨 agent 的"语言承诺"没有复核机制**。A 委托 B 的结果，B 回一句"done"，A 无法低成本验证。→ 设计约束：委托工具应支持 `verify_hint`（验证提示词/断言），执行完由调用方或规则层复核，而不是信"done"。

## 六、自主性的梯度：不是全有全无

**命题 6：自主性 = 在哪些决策点上让渡判断。**

自主性不是二进制开关（自主/不自主），而是**一组决策点的委托清单**：

| 决策点 | 例子 | 典型处置 |
|---|---|---|
| 事项的选择（做什么） | 用户说"优化"，agent 选优化哪块 | 人保留（或显式授权一次） |
| 路径的选择（怎么做） | 用什么算法、改哪个文件 | 可委托，但记录 |
| 执行的细节（动手） | 写代码、跑命令 | 委托 |
| 完成的判定（何时算完） | 验收标准是否达成 | 人保留（或独立验证者） |
| 事项的终结（取消/搁置） | 中止一个进行中的事项 | 人保留 |

"越权"的定义 = agent 在未获委托的决策点上做了决定。哲学上：**人类在事项系统中保留的是否决权，不是执行权。**

**工程映射：**
- 现有：`approval.rs`、`grant_agent_delegation`、`evolution` 的"人工介入硬通道"、`tool_loop` 的熔断——决策点清单已部分落地。
- 缺口：**决策点委托没有显式建模**，是散落在各处的布尔开关。→ 设计约束：事项对象应携带 `delegation_map: {choose: bool, path: bool, execute: bool, verify: bool, terminate: bool}`，每级默认 false（人类保留），agent 只能在被授权的决策点行使判断。

## 七、时间与死亡：事项的生命周期

**命题 7：事项活在时间里，死亡方式有四种。**

- **完成**：验收标准达成，债还清。健康死亡。
- **取消**：意图主体撤回承诺。有主死亡（必须由发起者发起）。
- **搁置**：意图休眠，事项悬置。半死状态——最危险，因为"未完成事项"会持续占用注意力/上下文，变成幽灵事项。
- **过期**：时间本身否定了事项（验收标准随世界变化失效）。自然死亡，但需要被登记，否则僵尸复活。

未关闭的事项是"活债"。多Agent系统里，上下文里塞满活债 = 认知负债，表现为"agent 老记得一堆没人要它做的事"。

**工程映射：**
- 现有：`evolution/snapshot.rs` 快照回滚、`convergence.rs` 收敛判据（max_rounds 防失控）、R53 的"跨日追踪"、reminder 系统——时间维度已有。
- 缺口：**没有事项死亡登记表**（completion/cancel/suspend/expire 四态 + 时间戳 + 原因 + 发起者）。→ 设计约束：新增 `matter_events` 表；幽灵事项检测（超过 N 天无进展且无验收判据的挂起事项）自动触发"终止或显式搁置"询问。

## 八、映射总表：哲学命题 ↔ 现有机制 ↔ 缺口

| # | 哲学命题 | 现有机制 | 缺口 → 设计约束 |
|---|---|---|---|
| 1 | 事项是差距不是物 | convergence.rs 收益分单度量 | 事项需携带 verifiable + 验收判据 |
| 2 | 意图转译会漂移 | approval.rs、grant_agent_delegation | 保留意图原句，收敛报告给"理解为X做成Y"对照 |
| 3 | 可分性是实用主义的 | delegate_to_agent 粒度由调用方定 | 分解需声明验收可加性，合不上记分解质量信号 |
| 4 | 发起/执行/验证三主体分离 | delegated_from、trace、幂等键 | verifier 实体化，verifier==executor 降可信 |
| 5 | 语言承诺 ≠ 世界事实 | sandbox、replay、参数 schema | 委托支持 verify_hint 复核 |
| 6 | 自主性是决策点委托 | approval、熔断、人工介入通道 | delegation_map 五决策点显式建模 |
| 7 | 事项四种死亡方式 | snapshot、convergence、跨日追踪 | matter_events 死亡登记 + 幽灵事项检测 |

## 九、下一步（可落地候选，按优先级）

1. **事项账本（matter ledger）**：把"差距→验收→执行→验证→死亡"显式建模为一条记录链。这是哲学命题 1/2/4/7 的合流点，也是其他约束的载体。
2. **验证者分离**：verifier 字段 + "执行者自证完成降级"规则。命题 4/5 的最小可落地切片。
3. **幽灵事项检测**：挂起无主事项自动触发"终止/搁置"询问。命题 7 的最小可落地切片。
4. **分解可加性声明**：delegate 时要求声明子验收判据与母验收判据的还原关系。命题 3 的落地。

> 建议先做 1（账本），因为 2/3/4 都只是账本上的字段与规则。账本可以先用 SQLite 表（`matter_ledger`）+ 记录函数落地，不侵入现有工具循环。
